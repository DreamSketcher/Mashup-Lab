# SRC: длительность, временная сетка и границы — проект для рассмотрения

**Статус: исследование; окончательный SRC-контракт не утверждён.** Это не
выбор библиотеки, не production-адаптер и не изменение проектных спецификаций.
Лицензия остаётся невыбранной. См. [предыдущее расследование](src-contract-and-samplerate-investigation.md).

Важно различать уже существующий и незакрытый уровни. Черновая
[audio-processing-specification](audio-processing-specification.md) и
`plan_project` **уже задают** длину *финального обработанного клипа* как
`round_half_up(N * Ft/Fs * duration_ratio)`, а нулевой результат отвергают.
План задаёт точные output границы, рендерер исполняет рассчитанный план. Он
не должен заново выводить их из музыкальных координат. Это действующее
черновое правило проекта, а не ещё не существующая опция. Одновременно
спецификация содержит общие слова о компенсации задержки и trim/pad, но
**не устанавливает**, какие frames SRC соответствуют каким координатам, как
подтверждать их корректность и когда trim/pad допустимы. Варианты ниже
показывают возможные трактовки; пересмотр принятого планового правила, если
потребуется, — отдельное согласование и изменение версии/тестов. Здесь ничего
не пересматривается и несовместимость не маскируется.

## Семантическая модель для сопоставления

Для анализа примем *в качестве гипотезы*: исходный клип содержит N исходных
frames, индекс `k=0..N-1`; frame `k` имеет момент `k/Fs`. Абсолютный исходный
диапазон `[a,a+N)` — границы в единицах source frames; клип начинается во
времени `a/Fs`, заканчивается в `(a+N)/Fs`, его локальный временной интервал
`[0, D)`, где `D=N/Fs`. Конец — граница, не дополнительный входной сэмпл.

Пусть output grid начинается в локальном 0 и `t(m)=m/Ft`, `u(m)=m*Fs/Ft`,
`m>=0`. Предположение о local-origin и рассматриваемые zero extension и reset
**ещё не приняты**. Оно не зависит от фактической позиции a на исходной сетке;
перенос результата на timeline с целым стартом S на rate Ft размещает output
frame m в `S+m`. При `duration_ratio=1` новый интервал длительности в проекте
`[S/Ft, (S+L)/Ft)`; после time-stretch размер плана определяется полным
`duration_ratio`, а не обязательно размером промежуточного SRC. Здесь
рассматривается только SRC и `duration_ratio=1`, если не сказано иное.

Интервал занимает время между границами, а sample — значение в конкретный
момент. Последний полученный sample не является «концом» клипа: например,
для L=1 он находится в t=0, а граница output — t=1/Ft. Даже если последняя
точка попала внутрь исходного интервала, её дискретный interval до следующего
frame может выйти за D. Нулевое продолжение — предположение о входе фильтра,
не разрешение вставлять нулевые **output** frames.

## Три варианта

Положим `q=N*Ft/Fs`, числа считать рационально, не через float.

| Модель | Определение | Интерпретация и последствия |
|---|---|---|
| **1. Длительность к ближайшему frame** | `L₁=floor(q+1/2)` для неотрицательных q, ties вверх. Output `[0,L₁)`; проектная длительность `L₁/Ft`. | Минимизирует абсолютную ошибку длительности: не более `1/(2Ft)`; при tie выбирается более длинная. Точки внутри исходного интервала могут быть **пропущены**. Существующий draft использует это правило для *финального* L при ratio=1, но не задаёт полноту сырого SRC output. |
| **2. Все точки внутри полуинтервала** | `L₂=ceil(q)` для N>0, для N=0 — 0; включает все и только `m>=0`, для которых `m/Ft < N/Fs`. | Все внутренние точки сохранены, точка ровно на конце исключена. Разница длительности `L₂/Ft - D` от 0 до менее `1/Ft`: output граница может быть позже D. Число frame intervals не является точной исходной длительностью. Несовместимость с текущим плановым L₁ в части случаев требует явно определённого согласования, а не замены формулы втихую. |
| **3. Контракт конкретного SRC API + отдельный план** | API выдаёт M frames с документированными координатами, boundary, latency, EOS и условиями; отдельно план требует L. M, первая координата и mapping не предполагаются из одного имени библиотеки. | Это не третья универсальная формула длины: API может иметь своё округление, startup и хвост. Требуется доказать соответствие каждого требуемого индексa m и обработать отсутствующие/лишние frames по **согласованному** правилу. При недоказанном соответствии — отклонить квалификацию, а не корректировать длину молча. |

При нашем предположении о нулевом origin `L₂-L₁` всегда 0 или 1: ближайшее
целое не может превысить ceil. Если они различаются, `m=L₁` имеет `u(m)<N`
и является последней точкой, исключённой моделью 1, но включённой моделью 2.
Сэмпл на `u=N` не включён ни в одну из них. Указанное справедливо для SRC без
stretch; при ином origin или нелинейной обработке формулы надо пересматривать.

### Примеры (точная арифметика)

| Fs → Ft | N | q=N·Ft/Fs | L₁ nearest | L₂ points | Последствие |
|---|---:|---:|---:|---:|---|
| 44100→48000 | 0 | 0 | 0 | 0 | Математически пусто; текущий проект пустой source range не допускает. |
| 44100→48000 | 1 | 160/147 | 1 | 2 | `u(1)=147/160 < 1`: точка внутри входа исключена L₁. |
| 44100→48000 | 2 | 320/147 | 2 | 3 | `u(2)=147/80 < 2`: ещё одна точка исключена L₁. |
| 44100→48000 | 10 | 1600/147 | 11 | 11 | Согласны; `u(10)=147/16 < 10`. |
| 44100→48000 | 441 | 480 | 480 | 480 | Конец `u(480)=441` исключён обеими моделями. |
| 48000→32000 | 1 | 2/3 | 1 | 1 | Точка только в 0, но output длится дольше исходника. |
| 48000→32000 | 2 | 4/3 | 1 | 2 | `u(1)=3/2 < 2`: ближайшая длительность пропускает эту точку. |
| 48000→24000 | 1 | 1/2 | 1 | 1 | Точное tie, округление вверх; ошибка +1/(2Ft). |
| 48000→16000 | 1 | 1/3 | 0 | 1 | L₁ даёт 0, но L₂ включает t=0. Текущий проект такой итог отвергает. |
| 32000→48000 | 1 | 3/2 | 2 | 2 | Точное tie, округление вверх; конец выходного интервала позже входного. |
| 48000→48000 | 2 | 2 | 2 | 2 | Identity: сетки и границы совпадают. |

Математический N=0 включён для полноты oracle, хотя валидный проект не
разрешает пустой источник клипа: `start_frame < end_frame`, итоговый L>0.
Аналогично `N=1, 48000→16000` сейчас приводится как математическая проверка,
не как разрешённое действие рендерера: в проекте target rate 48000, а
экспериментальный рендер вообще отклоняет ненулевой SRC.

Независимые клипы и округление не аддитивны. Например при 48000→32000 два
раздельных клипа N=1 имеют L₁=1+1, а один объединённый N=2 имеет L₁=1.
При 44100→48000 количество внутренних точек для двух N=1 равно 2+2, но
для N=2 — 3. Отдельный reset и локальный origin могут менять сигнал на
границе, даже когда длины совпадают. Поэтому модель A **не обещает**, что
разрезанный и целый клип дадут тот же временной результат или фазу; будущий
контракт должен определить, что происходит при соседних границах и каким
образом устанавливается placement, а не выводить непрерывность из одного L.

### API и согласование с планом: только диагностические примеры

Для модели 3 нужно от API или проверенного адаптера получить mapping:
какой frame j относится к какой координате, какая группировка/буферизация,
что остаётся после EOS, где начинается валидная область, как ведут себя
границы и каналы. Допущение `api_coordinate(j)=origin+j` в единицах output
frames даёт простую диагностику — **только если origin уже доказан**:

* План требует frames 0…479. API отдаёт 480 frames, origin=1: frame 0
  отсутствует, frame 480 лишний; равенство длины не доказывает alignment.
* При origin=−1 и 481 API frames все 480 плановых координат присутствуют,
  один output имеет координату −1; допустимое действие
  с этим frame и boundary по-прежнему нужно согласовать.
* При origin=1/2 ни один frame не совпадает точно с целой сеткой: простой
  trim/pad или сдвиг на целые frames не исправит фазу. Нужны иное отображение,
  вычисление на нужной фазе или отклонение реализации.
* При L=11 и M=10 с доказанным origin=0 не хватает координаты m=10; ноль
  не доказывает истинное значение. При L=480 и M=481 с origin=0 лишний frame
  m=480 не входит в выбранную целевую область; факт наличия дополнительного
  значения не доказывает, что остальные frames правильны.

Последние две ситуации похожи по длине на предыдущие опыты `samplerate`, но
**origin для них не установлен**; примеры не доказывают, какие конкретные
кадры были возвращены. Отдельный native API и wrapper имеют собственные
ограничения по consumed/flush — [см. результаты](src-contract-and-samplerate-investigation.md).

## Независимый математический oracle

[Исследовательский скрипт](../scripts/audio-research/src_grid_oracle.py)
использует только стандартную библиотеку Python; ни soxr, ни samplerate,
ни код проекта не импортируются. Он вычисляет обе длины, координаты и ошибки
через целые числа и `Fraction`, а также сравнивает индексы гипотетического API
с целевой сеткой **при явно заданном origin**. Это геометрический oracle, не
API-инструмент измерения задержки и не проверка фактической точности фильтра.
[JSON](evidence/audio-resampler-research/src-grid-examples.json) содержит
сгенерированные примеры, включая N=0/1/2 и дополнительные ratio.

Для амплитуды `ideal_value` независимо вычисляет идеализированную конечную
сумму нулево-продлённого входа с бесконечным sinc-ядром:
`c * Σ[k=0..N-1] x[k] sinc(c*(m*Fs/Ft-k))`, `c=min(1,Ft/Fs)`.
Рациональные позиции точны; sin и итог суммы — численные float64, не точная
арифметика или побитовый DSP oracle. Произвольный finite filter специально
не обязан совпадать с brick-wall идеалом: его полоса перехода, оконная функция,
края и фаза различаются. Даже при одинаковой временнóй модели необходимы
заранее согласованные полосы и допуски, а проверка impulse/DC не заменяет
полноценное качество. Функция вычисляет указанную координату и вне L; её
наличие **не означает**, что эта точка обязана попасть в output плана.

Тесты [test_src_grid_research.py](../tests/test_src_grid_research.py) проверяют
ручные примеры и tie, N=0/1/2, разные ratio, точку на исключённом конце,
перебор малых целых частот с независимым перечислением точек, инвариант
масштабирования частот, ошибки input, mapping со сдвигом и основные
аналитические свойства sinc. Они проверяют эту математическую модель, не
работу аудиодвижка и не качество коммерческого фильтра.

```sh
python3 scripts/audio-research/src_grid_oracle.py
python3 -m unittest discover -s tests -p test_src_grid_research.py -v
```

## Не смешивать четыре вида ошибок

1. **Длительность и количество:** разница L и заявленного output интервала;
   проверяется целочисленно по плану, независимо от амплитуд. Совпадение L
   не устанавливает alignment.
2. **Задержка/буферизация:** время готовности output или фиксированный сдвиг
   его координат — разные величины. Подать одинаковый input разными блоками,
   зафиксировать реальные output/consumed и EOS, затем сверить с full output;
   сравнить содержимое и координаты, а не только первый вызов с output.
3. **Phase alignment:** есть ли дробное или целое смещение сетки, и как меняется
   фаза с частотой. Анализировать внутренние импульсы, синусы и по возможности
   комплексный transfer function; пик импульса сам по себе не определяет
   дробный сдвиг или частотно-зависимую фазу. Fractional mismatch нельзя
   исправить изменением одного счётчика длины.
4. **Качество фильтра:** passband ripple, stopband/alias, форма перехода,
   ringing, транзиенты и слуховая оценка — со стабильными фикстурами и
   согласованными критериями. Отличия от идеального sinc на краю не означают
   дефект, а нулевой phase offset не гарантирует качество.

## Проект окончательного контракта: решения владельца ещё нужны

Ниже структура будущего соглашения, **не утверждённый стандарт**:

* **Временная модель:** определить момент начала и конца входного клипа,
  фазу локального output grid относительно начала; утвердить или заменить
  гипотезы выше. Решить поведение N=0 и случая нулевой финальной длины с
  учётом текущей валидации, не превращая их молча в тишину.
* **Длина и операции:** подтвердить или пересмотреть текущее L плана для всех
  `duration_ratio`; отдельно определить допустимые L промежуточного SRC и
  отношения к целевой области, включая случаи L₁≠L₂ и недостающий валидный
  frame. Рендерер использует границы свежего плана, не вычисляет второй план.
* **Границы и состояние:** утвердить либо отвергнуть crop-first, zero extension,
  reset на независимый клип и local-origin; описать каналы и источник контекста,
  last input/EOS/flush и пустой вход. Разрезанные клипы не обязаны воспроизводить
  цельный сигнал без отдельного требования.
* **Соответствие API:** зафиксировать для конкретной версии алгоритма таблицу
  `j → m` и валидную область, задержку и фазу; определить, какие доказанные
  действия с реальными хвостами/префиксами допустимы, как обрабатывать
  недостающие значения и сигнализировать ошибку. Не принимать trim/pad
  только потому, что размер отличается, и не считать pad эквивалентом выборки.
* **Приёмка:** до сравнения библиотек согласовать пороги для ориентира,
  DC/impulses на краях, tone/sweep, stereo, ratio, коротких клипов, состояний,
  размеров блоков и разделения клипов. Затем Windows на Python 3.11–3.13 с
  точными wheels, лицензиями, сборками и реальными прослушиваниями. Применить
  отдельный release gate к уже используемому soundfile/libsndfile.

Этот документ не решает перечисленные вопросы за владельца и не отменяет
уже существующую draft-спецификацию. До решения коллизии между её общим
trim/pad и требованием доказать координаты нельзя заявлять их полностью
согласованными или включать SRC в production.
