# SRC и границы плана: проект контракта для рассмотрения

**Статус: проект, не утверждён.** Ни SRC, ни time-stretch, ни лицензия не
выбраны; production-код и действующие спецификации не меняются. Это
продолжение [анализа временной сетки](src-length-grid-contract-proposal.md).
Проверки ниже — искусственные модели, не квалификация реального DSP.

## Уже существующие решения и границы этого этапа

* В текущем draft проекта Planner задаёт финальную длину
  `L = round_half_up(N * Ft / Fs * r)`, где `r=duration_ratio` — множитель
  **длительности**, а не скорости. Он считает это выражение точно, одним
  округлением, rejects `L=0` и пустой source range. `Ft=48000` в MVP.
  Границы каждого клипа `[S,S+L)` и overlaps задаются свежим планом;
  рендерер их исполняет, не строит параллельную геометрию. Смена этого
  правила — отдельное решение, здесь не предлагается его менять.
* A — независимая обработка клипов; единая processing graph и streaming не
  являются обязательными условиями MVP. Нормализация длины в существующей
  [draft-спецификации](audio-processing-specification.md) описана общими
  словами «trim end or pad silence at end». Дополнительный контракт о
  координатах ещё не согласован; его нельзя выдавать за уже действующую
  реализацию или за беспроблемное уточнение этих слов.
* Термины **доказанный mapping** и **валидация** ниже означают конкретную
  квалификацию выбранного API, версии, профиля и реализованного adapter на
  тестах и по документации. Наличие длины, поля metadata или присвоенных
  номеров не является доказательством. Доказательство не означает
  математической верификации любой возможной платформы.

## Плановая длина и промежуточная длина

Обозначим `q=N*Ft/Fs`, `R=round_half_up(q)` как *геометрический ориентир*
SRC без stretch, `L=round_half_up(q*r)` — финальная длина плана, `M` — число
реально выданных API frames. Ни R, ни L **сами не задают** M, задержку или
состав валидной области. Сравнение `M` и `L` информативно для r=1 после
подтверждения единой сетки; при r≠1 сравниваются разные стадии и по их
неравенству нельзя устанавливать недостачу или избыток.

Модель исследовательского mock downstream ниже требует для финального кадра
`m` значения на промежуточной сетке в `p=m/r`, с линейной интерполяцией
целочисленных соседей; при целом p второй сосед не требуется. Это лишь
**искусственный пример зависимостей** и не time-stretch: такое отображение
меняет высоту тона. Реальный pitch-preserving time-stretch может иметь
нелинейное внутреннее преобразование, фильтровую поддержку, историю, задержку
и другие потребности в хвосте; его поддержку нельзя выводить из `m/r`.
Столбец support не является нормой для реального backend.

| N, Fs→Ft | r | R (ориентир SRC) | L плана | Пример support mock downstream / вывод |
|---|---:|---:|---:|---|
| 1, 44100→48000 | 1 | 1 | 1 | Требуется `0`; точка сетки `1` внутри входного интервала, но не включена в план. |
| 2, 44100→48000 | 1 | 2 | 2 | Требуются `0,1`; совпадение количества не проверяет mapping. |
| 10, 44100→48000 | 1 | 11 | 11 | Требуются `0..10`; API с M=10 и origin 0 не покрывает план. |
| 441, 44100→48000 | 1 | 480 | 480 | Требуются `0..479`; корректно установленный дополнительный frame не нужен финальному результату. |
| 441, 44100→48000 | 0.96 | 480 | 461 | Mock требует `0..480`: несмотря на L<R, при линейном support нужен frame 480; нули вставлять нельзя. |
| 441, 44100→48000 | 1.04 | 480 | 499 | Mock требует `0..479`: L>R не означает нехватку 19 промежуточных кадров. |
| 2, 48000→48000 | 0.5 | 2 | 1 | Mock требует только `0`; это не обещание реального pitch-preserving stretch. |
| 2, 48000→48000 | 2 | 2 | 4 | Mock требует `0..2`: frame 2 лежит на конце исходного интервала; допустимость его вычисления зависит от boundary policy. |
| 1, 96000→48000 | 0.5 | 1 | 0 | Математический случай отвергается текущим проектом из-за L=0. |
| 1, 96000→48000 | 2 | 1 | 1 | Прямое округление final даёт 1; `round_half_up(R*2)` дало бы 2 и неверный план. |

Данные таблицы, включая набор support в этой игрушечной модели,
[воспроизводимы](evidence/audio-resampler-research/src-plan-mapping-model.json).
Например для r=0.96 последний final index 460 обращается к промежуточной
координате `460 / 0.96 = 479 + 1/6`; линейная схема требует `479` и `480`.
Это не означает, что реальный stretcher обязательно требует frame 480: он
может использовать совсем другую поддержку и boundary policy. Необходимо
уточнить его контракт и проверить, какие входные данные нужны для выполнения
планового интервала. Нельзя удалить intermediate frames только потому, что
их номера больше L конечной стадии.

### Когда API даёт меньше, ровно или больше чем L при r=1

При условии, что valid API output покрывает смежную целочисленную сетку с
origin 0 (это **допущение**, не результат для произвольной библиотеки):

| Выдача | Позиции | Предварительная интерпретация |
|---|---|---|
| `M<L` | `0..M-1` | Отсутствуют `M..L-1`; error или отдельно согласованный способ получить **правильные значения**. |
| `M=L` | `0..L-1` | Количественно достаточно, но качество, реальные координаты, границы и все каналы ещё требуют подтверждения. |
| `M>L` | `0..M-1` | Есть кандидаты на использование `0..L-1`, остальные — кандидаты на исключение после проверки mapping и downstream; это не отбрасывание по размеру без проверки. |
| `M=L`, origin=1 | `1..L` | Не хватает `0`; `L` лишний. Одного сравнения длин недостаточно. |
| любая M, origin=1/2 | `1/2,3/2,...` | Ни одна точка не совпадает с целой сеткой; нельзя исправить обрезкой или целочисленным сдвигом. |

Числа из Linux-исследования (на отдельных фиксированных сборках и one-shot):
при `N=44100`, 44100→48000, r=1, `L=48000`; `samplerate` дал M=48000
mono и M=48001 stereo. При N=10 mono, `L=11`, API дал 10. Это **наблюдения
длины**, не подтверждённый origin/frame mapping для этих случаев. Не делаем
вывод, что один конкретный frame можно удалить или восстановить. Подробности
EOS и native wrapper — в [расследовании](src-contract-and-samplerate-investigation.md).

## Проект правил по стадиям (на согласование)

Ниже — рекомендуемый для обсуждения инвариант, а не принятая спецификация:

1. **Plan:** источник правды для финальных `S,L` — свежий валидированный план;
   данные исходника и параметров берутся из проекта. В проекте `L>0`.
2. **Crop и SRC:** независимо для каждого клипа на отдельном состоянии
   получить значения, которые downstream действительно потребует; плановая L
   не диктует безусловное M промежуточного SRC. Передать/учесть границы входа,
   внутреннюю/внешнюю задержку, consumed, EOS, flush, числа каналов и mapping.
   Для r=1 предлагается исследовать local-origin сетку `m*Fs/Ft`, с нулевым
   продолжением и reset, но **выбор границы/фазы ещё не принят**. Физический
   input outside clip и математическое продолжение — разные понятия.
3. **Duration и pitch:** для r=1 и pitch=0 сохранить контракт bypass без
   незаявленного преобразования. При r≠1 проверить отдельный алгоритм,
   необходимый input support, его reset, phase/latency, выходной mapping и
   границы — одних формул длины и SRC недостаточно. Pitch shift должен сохранять
   финальную длительность; реальный алгоритм может требовать внутреннего
   контекста и меняет содержимое. Параметры неподдерживаемых стадий должны
   отклоняться, как и сейчас, до отдельной интеграции.
4. **Alignment/selection:** если все выходы, необходимые downstream и финальной
   области `[0,L)`, подтверждены по координатам, каналам, boundary и выбранному
   numerical profile, возможно извлечь эту область по mapping. Выбрасывать
   дополнительные frames можно лишь когда подтверждено, что они не нужны
   ни одной последующей стадии; сохранять правильную обработку краёв. Начальную
   задержку можно компенсировать только при доказанном целочисленном mapping
   и наличии всех целевых значений, а не сдвигом на произвольный peak impulse.
5. **При недостатке данных:** если хотя бы одно обязательное значение не
   получено, mapping неизвестен или дробный, предлагается ошибка, пока не
   принят и не проверен специальный механизм вычисления/компенсации. Дополнение
   нулями, копирование края, интерполяция или дробный сдвиг — разные алгоритмы
   с качественными и граничными последствиями; лишь отдельное утверждение
   такого механизма может сделать его допустимым. Пропуск NaN/Inf недопустим
   согласно существующему draft; подмена отсутствующих данных тишиной скрывает
   ошибку.
6. **Сведение:** только после подтверждения финальной области и обработки
   gain/pan/fades разместить ровно её в `[S,S+L)`. Одни номера frames не
   доказывают корректные значения, качество, отсутствие artifacts или
   воспроизводимость на другой платформе.

Спецификация сегодня допускает общее trim/pad; предложение об ошибке при
недоказанном mapping **строже и потенциально меняет смысл**. До согласования
владельцем и последующего явного изменения спецификации противоречие остаётся
открытым. Ни этот документ, ни mock-код не уполномочивают production менять
поведение.

## Проверки на искусственных сигналах

Независимый [mock-протокол](../scripts/audio-research/src_plan_mapping_model.py)
и [тесты](../tests/test_src_plan_mapping_research.py) используют только
стандартную библиотеку и соседний математический oracle. Синтетический API
вычисляет float64-значения идеального sinc с предполагаемым zero extension
и снабжает их **сконструированными**, заранее известными координатами. Это
контролируемая предпосылка теста, а не доказательство, что реальный API
предоставляет или правильно маркирует координаты. Например metadata легко
соврать; флаг в mock лишь моделирует результат внешней квалификации.

Покрыто:

* r=1, импульс и дополнительные известные координаты: выбираются требуемые
  данные; отсутствующий последний кадр, сдвиг origin, дробная сетка, дубликат
  и неподтверждённый mapping приводят к ошибке без pad и переклейки ярлыков.
* Длительность считается одним точным округлением; сравниваются r=0.5,
  0.96, 1, 1.04 и 2. Для игрушечного r=0.96 проверено, что при L=461 ещё
  требуется 481-я промежуточная координата, и линейная интерполяция рампы
  даёт ожидаемое численное значение. r=2 для N=2 демонстрирует аналогичную
  необходимость boundary support. Качество time-stretch не исследуется.
* Три **синтетических** независимых stereo-клипа — импульс, DC и сигнал у
  границы — вырезаются из двух источников с разными внешними значениями;
  mock получает только clip, начальное состояние не переносится, выходы в
  каждом сравнении одинаковы. Размещение по фиксированным synthetic `S,L` и
  паузы между клипами также проверены. Это тест конструкции crop-first, не
  проверка реального рендерера или доказательство совпадения цельной записи
  и её разрезанных частей.
* N=0 и L=0 присутствуют только как математические состояния модели; они не
  превращены в допустимые проектные клипы.

```sh
python3 scripts/audio-research/src_plan_mapping_model.py
python3 -m unittest discover -s tests -p 'test_src*research.py' -v
```

## Что нужно решить до утверждения и квалификации

1. Согласовать temporal origin, zero extension/reset, local phase, трактовку
   начального/конечного sample и поведения точных/дробных задержек — варианты
   остаются открыты. Утвердить или изменить более строгую error/compensation
   политику и согласовать с нынешним trim/pad в draft.
2. Определить контракт финальной стадии с r≠1 и pitch, достаточный support и
   поведение на очень коротких клипах. Не использовать игрушечную линейную
   интерполяцию как pitch-preserving обработчик. Согласовать спектральные,
   фазовые и численные допуски с независимым reference, а также явно разделить
   ошибку длины, задержку, phase alignment и качество фильтра.
3. Для каждого будущего API установить соответствие координат по документации
   и независимым тестам: импульсы в разных положениях, частоты, stereo,
   boundary, повторный reset, разные размеры блоков, потребление и flush;
   сформировать набор допустимых преобразований результата и failure modes.
4. Затем квалифицировать выбранные версии на Windows с Python 3.11–3.13,
   фактические wheels/DLL и licensing включая уже используемый soundfile. Нужны
   прослушивание, точные профили и результаты CI; предварительные wheel-срезы и
   Linux mock не равны Windows qualification.

Решений по лицензии, SRC и конкретной компенсации нет. Не исправлять
спецификацию или подключать DSP до рассмотрения и отдельного разрешения.

Для следующего решения владельца: [краткие предложения по границам DSP](audio-boundary-decisions-for-review.md), включая проект замены текста спецификации без её изменения.
