# Timeline plan — draft v0.1

`python -m mashup plan project.yaml` validates the project and source files,
then writes one JSON object to stdout. Diagnostics go to stderr and failures
return a nonzero exit code. The plan is a derived, read-only timing artifact;
it is not a replacement for the project or a complete audio processing graph.

```json
{
  "plan_version": "0.1",
  "sample_rate": 48000,
  "clips": [
    {"id": "verse", "start_frame": 0, "end_frame": 48000, "duration_frames": 48000}
  ],
  "overlaps": [],
  "total_frames": 48000
}
```

All frame values are nonnegative integers in the output sample rate. Ranges
are zero-based, half-open `[start_frame, end_frame)`; duration equals end minus
start. The clips array contains every project clip, including isolated clips, and
preserves project order, which is also mixing order. An empty clip list is
invalid in v0.1; there is no empty-plan special case.
The total is the maximum clip end, including any leading or intermediate
silence. `overlaps` lists every unordered pair whose intervals actually
intersect, in nested project clip order; boundary touching is not an overlap.
Pairs are generated by source-list indices `i < j`, not by ID or start time;
`first_clip_id` always refers to the earlier project element, even for equal
starts. Each overlap is an object with `first_clip_id`, `second_clip_id`, `start_frame`,
`end_frame`, and `duration_frames`. Three simultaneous clips produce three
pairwise entries, not a separate three-way interval.

For the same verified project and sources the parsed JSON values and array order
are stable; consumers must not depend on whitespace or object key order. This
is a draft interface: incompatible changes require a different `plan_version`.
The plan does not include source hashes, input boundaries, effects, or render
profile; a future renderer must consume it together with the validated project
and environment, verify they match, and use its frame positions and lengths
rather than independently recomputing musical coordinates. A standalone,
self-contained execution plan and project/plan binding remain future work.

## Independent validation

`python -m mashup validate-plan plan.json` validates the plan without the source
project. It checks the exact field set and version, sample rate, nonempty clip
list, unique valid clip IDs, integer nonnegative boundaries, positive clip
durations equal to end minus start, and `total_frames` equal to the maximum end.
It also checks that the overlap list is exactly the ordered set of all positive
pairwise intersections of the listed clips: references exist, start is the
maximum of the two starts, end is the minimum of the ends, and duration is
positive and equals end minus start. Duplicate JSON keys and nonstandard
NaN/Infinity constants are rejected.

A valid plan is not proof that it matches a particular project: absent project
and source hashes, it cannot detect a stale plan or verify that clips were
omitted relative to the project. Binding a plan to the exact project, source
identities and engine version is future work, as is checking the processing
profile before rendering. Until then, regenerate the plan from the current
validated project; do not use a stored plan for rendering.

## Numeric and resource considerations

Frame positions are JSON integers and may exceed 2^53 - 1: consumers must use
an arbitrary-precision integer JSON parser or otherwise reject values they cannot
represent exactly (ordinary JavaScript `Number` cannot do so). The draft does
not define a maximum BPM, bar number, clip count or duration. Both plan
construction and independent overlap validation inspect clip pairs; a densely
overlapping project has `n * (n - 1) / 2` overlap entries. Callers handling
untrusted or large projects should impose their own resource limits; successful
validation is not a performance or safety guarantee for arbitrarily large inputs.
