## Проект эталонной модели для обсуждения

Это явный тестовый **кандидат**, а не изменение действующего контракта:

1. Вход — целочисленные frame indices `[a, b)` исходника, `N=b-a`, общие для
   всех каналов. Только этот участок передаётся отдельному независимому
   экземпляру преобразования. `Fs > 0`, `Ft > 0` — целые частоты. Пустой
   участок рассматривается отдельно и не передаётся в данные API в этом опыте.
2. Локальная координата исходного кадра для выхода `m >= 0` — **точное
   рациональное** `u(m) = m * Fs / Ft`, где `m=0` совпадает с локальным
   входным frame 0. Время `u/Fs`, без глобального сдвига фазы из-за `a`.
   Если исходный диапазон начинается в 137, сетка по-прежнему начинается в
   его собственном frame 0. При размещении клипа глобальная позиция задаётся
   отдельно планом; это не сдвиг фазы ресемплера.
3. Кандидат числа выходных кадров — `L = floor(N * Ft / Fs + 1/2)` с точной
   целочисленной арифметикой для неотрицательных значений; допустимые индексы
   `0 <= m < L`. Пример: N=10, 44100→48000, L=11, `u(10)=9.1875`;
   N=441, L=480, `u(479)=440.08125`. Это именно геометрическая договорённость,
   она не следует автоматически из фильтра, EOS или интервала `u < N`.
   Обсудить ties, очень короткие входы (L может быть 0), пустой клип и связь
   с существующими правилами планировщика до утверждения.
4. Для кандидата границы: `x[k]=0` для `k<0` и `k>=N`; соседние сэмплы
   исходника не входят в состояние. Состояние/история фильтра сбрасывается
   между клипами. Никаких скрытых предыдущих/последующих frames. Это не означает,
   что текущие wrappers документированно удовлетворяют такому правилу.
5. Идеализированный ориентир: для каждого канала, при `c=min(1,Ft/Fs)`,
   `y_ideal[m] = c * sum(k=0..N-1) x[k] * sinc(c*(u(m)-k))`,
   `sinc(z)=sin(pi*z)/(pi*z)`, `sinc(0)=1`. Это бесконечный во времени
   идеальный low-pass при нулевом продолжении, сумма конечна по входу.
   Для impulse в `k` единственный член формулы даёт конкретное число в любой
   координате, включая края. Реальные FIR-фильтры имеют полосу перехода,
   конечную длину и разные характеристики: **точное совпадение с этим ideal
   не требуется и не показано**. Допуски амплитуды, спектра и фазы должны
   быть согласованы по требованиям к музыке, до оценивания библиотеки.
6. Идеальная компенсация временного сдвига в этой модели — ноль: импульс
   в исходном k расположен вокруг `m=k*Ft/Fs` на сетке выхода, не обязательно
   в целом frame. Выход 0 предназначен для `u=0`. Computational latency
   (число входов до первого доступного выхода) — отдельная величина и не есть
   автоматический сдвиг содержимого. При streaming нужно сохранить/слить
   реальный хвост и доказать соответствие сетке; вызов EOS и факт равной длины
   не доказывают alignment. Не применять обрезку, zero-fill или задержку,
   пока не проверено содержание и координаты *каждого* необходимого кадра.

Эталонная сумма выше задаёт математический идеал, но ещё не является полноценным
oracle для выбранного finite filter: нужны согласованные passband/stopband,
ошибки, тестовые пороги, привязка сетки к границам плана и независимая
реализация для тестов. Не сравнивать прямо побитовое значение ideal с output.

## Исследование C API против wrapper

[python-samplerate v0.2.4](https://github.com/tuxu/python-samplerate/blob/v0.2.4/src/samplerate.cpp)
выделяет на каждом `Resampler.process` выходной массив вместимостью
`ceil(input_frames * ratio)`, вызывает `src_process` один раз, отдаёт только
сгенерированный массив и не возвращает `input_frames_used` вызывающему коду.
Для пустого input эта ёмкость равна нулю. Native
[full API 0.2.2](https://github.com/libsndfile/libsamplerate/blob/0.2.2/docs/api_full.md)
возвращает consumed и generated; вызывающий код должен учитывать частично
потреблённый вход. `src_simple` в этой версии создаёт состояние, устанавливает
EOS, делает один `src_process` и освобождает состояние
([source](https://github.com/libsndfile/libsamplerate/blob/0.2.2/src/samplerate.c)).

Эксперимент собрал **отдельную** `libsamplerate 0.2.2` из исходников и вызвал
её через ctypes; это не бинарник внутри wheel, поэтому совпадение не доказывает
их идентичную сборку или весь контракт. В native-протоколе использован отдельный
output buffer на 256 frames, оставшийся вход подаётся повторно по счётчику
consumed, EOS ставится на последнем участке, затем подаются пустые входы с
**ненулевой output capacity** до нулевого output. Эту процедуру исследуем для
этой версии, а не предписываем будущему адаптеру без дополнительных тестов.

### Результаты

* Mono tone, 44100 frames, 44.1→48 kHz, blocks 1024: ранее wrapper дал
  47845 frames против 48000 one-shot. В точной эмуляции wrapper на отдельной
  native-сборке результат битово совпал с wrapper на данном входе; 44100
  входных frames потреблены, неполного входа в этой серии не было. Последний
  вызов: input 68, output capacity 75, EOS=true, generated 75. Следовательно,
  буфер заполнен, но это само по себе не доказывает, сколько осталось.
* После этой же серии native `src_process` с пустым input, ненулевым output
  buffer и EOS выдал **ещё 155 настоящих frames**, после чего 0. Префикс и
  хвост вместе битово совпали с native полной обработкой на этой машине
  (48000). Пустой вызов через wrapper имеет нулевую ёмкость; прежняя попытка
  с добавлением входных нулей — не корректная демонстрация flush. Для данного
  опыта причина потери результата — исчерпанная output capacity при EOS и
  отсутствие способа выделить output для empty-input drain в этом методе;
  не утверждаем, что все проблемы streaming сводятся только к этому.
* При native блоках 1024 и output capacity 256 наблюдалось 78 вызовов с
  неполным потреблением по всем случаям. Harness повторно подавал остаток;
  wrapper не сообщает consumed, поэтому нельзя вообще считать полное
  потребление гарантированным. Для 127/1 и этой ёмкости в данных случаях
  partial calls не было. Неизвестно, возникает ли неполное потребление с
  wrapper capacity на иных входах, частотах и размерах.
* Всего 60 комбинаций: 2 частотные пары (44100→48000, 48000→32000), mono и
  stereo, N=1/10/100/441/4096, impulse первый/последний frame и тон 997 Hz.
  Для каждой native simple (буфер больше входа), native streaming с блоками
  1/127/1024 и ёмкостью 256 дал точное совпадение при полном consumed и drain
  в этом окружении: 180/180 сравнений. Wrapper one-shot совпал с native simple
  60/60; соотношение wrapper stream/native simple зависит от размера блока
  (точное совпадение 12/60, 36/60 и 48/60 соответственно). Для soxr stream
  vs one-shot — 180/180 точных совпадений. Это не гарантия для других данных,
  библиотек, частот, окружений и способов chunking.
* Разница one-shot не только в Python-распределении буфера: native simple с
  **большой** ёмкостью тоже вернул 10 frames для mono N=10 (кандидат L=11)
  и 481 для stereo N=441 (кандидат L=480). Значение выходного frame 10 в
  mono N=10 отсутствует; для импульса в frame 9 идеальная sinc-модель даёт
  там 0.943165, soxr возвращает 0.906882. Эти значения не взаимозаменяемы;
  добавлять ноль нельзя считать восстановлением сигнала. Для stereo N=441
  native выдаёт и frame 480; его смысл по выбранной сетке требует анализа.
  Никакая обрезка не утверждается автоматически.
* В [native `src_sinc.c` 0.2.2](https://github.com/libsndfile/libsamplerate/blob/0.2.2/src/src_sinc.c)
  у mono и stereo путей разный код завершения (`>` и `>=`), и внутренние
  индексы для каналов масштабируются. Это основание исследовать разницу длин,
  не окончательное доказательство механизма для всех конфигураций. Расхождение
  одного кадра не названо defect без подтверждения контракта upstream.
* Для N=10, импульса в первом frame идеальный sinc на m=0 равен 1, native —
  0.965728, soxr — 0.913240. Для downsample 48000→32000, N=100, k=0,
  идеал 0.666667, native 0.643819, soxr 0.637915. Это иллюстрация отличий
  конкретных фильтров и фаз, **не** качество/ошибка относительно согласованного
  допуска. По данным отдельных пиков нельзя полностью установить group delay.
* Независимость входа: случайный одинаковый участок `[137,578)` помещён в два
  разных соседних контекста, вырезан до вызова, свежий one-shot: для каждого
  wrapper выходы совпали битово. Такой эксперимент подтверждает лишь механизм
  crop-first в скрипте (обоим вызовам физически переданы одинаковые массивы),
  а не изоляцию будущего рендерера. Non-grid-aligned начало 137 проверяет, что
  в исследовательском вызове не передаётся глобальная координата, но не
  доказывает фазу для будущего адаптера.

## Воспроизведение и ограничения

Данные и все 60 случаев: [JSON](evidence/audio-resampler-research/samplerate-native-linux.json),
скрипт: [investigate_samplerate.py](../scripts/audio-research/investigate_samplerate.py).
Последовательность ниже — в `/tmp`, не в проектном окружении; требуется Linux,
компилятор, доступ к GitHub/PyPI. На машине опыта Python 3.11.2, GCC 12.2.0,
NumPy 2.4.6, soxr 1.1.0, samplerate 0.2.4 и CMake 3.31.10.
Исходный tarball 0.2.2 SHA-256:
`16e881487f184250deb4fcb60432d7556ab12cb58caea71ef23960aec6c0405a`.
Хеш собранной `.so` приведён в JSON, но он может отличаться при пересборке.

```sh
python3 -m venv /tmp/mashup-native-src
/tmp/mashup-native-src/bin/pip install numpy==2.4.6 soxr==1.1.0 samplerate==0.2.4 cmake==3.31.10
curl -L https://codeload.github.com/libsndfile/libsamplerate/tar.gz/refs/tags/0.2.2 -o /tmp/libsamplerate-0.2.2.tar.gz
sha256sum /tmp/libsamplerate-0.2.2.tar.gz  # compare with hash above before extracting
tar -xzf /tmp/libsamplerate-0.2.2.tar.gz -C /tmp
/tmp/mashup-native-src/bin/cmake -S /tmp/libsamplerate-0.2.2 -B /tmp/libsamplerate-build -DBUILD_SHARED_LIBS=ON -DLIBSAMPLERATE_EXAMPLES=OFF -DLIBSAMPLERATE_TESTS=OFF -DCMAKE_BUILD_TYPE=Release
/tmp/mashup-native-src/bin/cmake --build /tmp/libsamplerate-build -j2
LIBSAMPLERATE_SO=/tmp/libsamplerate-build/src/libsamplerate.so /tmp/mashup-native-src/bin/python scripts/audio-research/investigate_samplerate.py > /tmp/src-result.json
```

Это исследование не запускает upstream tests и не проверяет формально floating
point environment, процессорные различия, sweep, музыкальные транзиенты,
качественные фильтры или OS Windows. Не измеряет память, не обосновывает
победителя. Direct C эксперимент не разрешает подключение native к движку.

## До квалификации

* Согласовать описанную модель с планировщиком и отдельно правила N=0, крайних
  ratio, округления и внутренней точности. Разработать независимый вычислитель
  ideal и утверждённые допуски конечного фильтра.
* Проверить фазу и смещение для серии внутренних и граничных импульсов,
  не только nearest-frame peak; свойства DC, sweep, alias и задержку;
  исключить попадание контекста за границами клипа в реальном адаптере.
* Исследовать native обработку с ограниченными буферами, нулевыми входами,
  финальным EOS на всех случаях и документированными инвариантами; отличать
  unconsumed input, buffered output и валидные кадры за границей L.
* После согласования контракта выполнить Windows тесты на поддерживаемых
  Python 3.11–3.13 и конкретных pinned wheels, включая извлечение/проверку
  их состава и лицензий. Windows wheel CPython 3.14 из предыдущего отчёта не
  квалифицирует текущие CI версии. Аудит `soundfile`/`libsndfile` и встроенных
  codecs — актуальный release gate независимо от выбора будущего SRC.
* Прослушивание, reproducibility across environments и юридическая проверка —
  отдельные незакрытые этапы. Проверки CI для `4a23075` пользователем не
  обнаружены; отсутствие статусов не означает ни success, ни failure.
