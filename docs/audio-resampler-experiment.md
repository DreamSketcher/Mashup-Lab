# Изолированное сравнение ресемплеров: предварительное наблюдение

Исследование, **не выбор зависимости и не проверка реализации варианта A**.
Production, `requirements.txt`, проектный `.venv` и спецификации не менялись.
Исходный вариант A и обсуждаемые нулевые границы — в [рекомендациях](audio-engine-architecture-recommendations.md).

## Метод

Временное venv вне репозитория, Linux x86-64, Python 3.11.2, NumPy 2.4.6;
`soxr==1.1.0` (libsoxr `0.1.3-14-ga66f3ee`, HQ),
`samplerate==0.2.4` (libsamplerate 0.2.2, `sinc_best`). Кандидаты получают
одинаковые float32 массивы, 44.1→48 кГц и 48→32 кГц; preset не гарантирует
равной частотной характеристики, поэтому время не является честным общим
рейтингом. Они загружены в одну временную исследовательскую среду, но не
поставляются с продуктом. Используется публичный API Python wrappers, не прямой
C API. Модель input/output и ограничения wrapper входят в результаты.

Выполненный сценарий: [compare_resamplers.py](../scripts/audio-research/compare_resamplers.py);
полный вывод: [linux-x86_64.json](evidence/audio-resampler-research/linux-x86_64.json).
Запуск в *новом* временном окружении, не в `.venv` проекта:

```sh
python -m venv /tmp/mashup-src-exp
/tmp/mashup-src-exp/bin/pip install numpy==2.4.6 soxr==1.1.0 samplerate==0.2.4
/tmp/mashup-src-exp/bin/python scripts/audio-research/compare_resamplers.py
```

Генерируются тишина, импульс, тон 1 kHz, два связанных канала, короткие
постоянные сигналы, линейный sweep 100–20000 Hz и тон 18 kHz для downsampling. Для streaming один и тот же
тон подаётся кусками 127/1024/4096 frames, последний отмечается EOS. Источники
не файлы пользователей; нет воспроизведения/прослушивания. Текущая формула
half-up используется только как **геометрический ориентир**. Мы не задавали
заранее пороги на спектральное качество и блоковую эквивалентность, поэтому это
не сравнительное приёмочное испытание. Мера скорости — пять замеров one-shot
после остальных операций, без контроля CPU/scheduling и без статистического
исследования. Никаких обобщённых оценок качества по ней не делаем.

## Результаты конкретного запуска

| Измерение | soxr HQ | samplerate sinc_best |
|---|---:|---:|
| 1 секунда mono, 44100→48000 | 48000 frames | 48000 frames |
| 1 секунда stereo, те же данные | 48000 frames | 48001 frames |
| 10 mono frames → ожидаемые 11 | 11 | 10 |
| 100 mono frames → ожидаемые 109 | 109 | 108 |
| Импульс в input 5000: максимум | output 5442 | output 5442 |
| Тишина | peak 0 | peak 0 |
| Повтор one-shot тех же фикстур | точное совпадение на этой машине | точное совпадение на этой машине |
| Stereo: ошибка отношения R=0.5L | 0 для данной фикстуры | 0 для данной фикстуры |
| Тон 1 kHz: stream 127 / 1024 / 4096 | 48000 frames, битово как one-shot | 47844 / 47845 / 47844, не совпадают по длине |
| Простейшее измерение alias: 18 kHz → 14 kHz при 48→32 | −147.50 dB относительно входного пика | −147.68 dB относительно входного пика |
| Медианное wall time, 5 с mono, 5 вызовов | ~0.0019 с | ~0.144 с |

Сравнивался результат внутри одного фиксированного окружения, не между
библиотеками; одинаковое расположение пика импульса не доказывает идеального
совпадения задержки, phase response или музыкального транзиента. Alias — только
амплитуда **одной** синусоиды 14 kHz после исключения 2048 frames с каждой
стороны; это не спектральная маска, stopband certification или измерение SNR.
Пики/хеши и отдельные замеры находятся в JSON. На других CPU/версиях могут
различаться даже при тех же входах.

**Особенно важно:** наивный streaming-пример `samplerate` не обеспечил полную
длину. Нельзя считать это окончательным свойством libsamplerate или доказательством
ошибки DSP: возможны неправильный протокол/адаптер или особенности wrapper.
Дополнительная проба после EOS: пустые блоки выдали 0, а последующий блок из
1000 нулей выдал ещё 155 frames для chunk 1024; это наблюдение, а не
валидированная процедура flush. В [source wrapper v0.2.4](https://github.com/tuxu/python-samplerate/blob/v0.2.4/src/samplerate.cpp)
`Resampler.process` вызывает `src_process`, возвращает output и не возвращает
потребителю `input_frames_used`; поэтому надо отдельно изучить семантику
потребления, EOF и zero padding, а не просто дополнять результат нулями до
нужной длины. Та же реализация ограничивает размер output одним `ceil` на блок.
Результаты не удостоверяют корректность работы после добавления нулей.

Отдельная наблюдаемая разница длины stereo/mono `samplerate.resample`: wrapper и
native библиотека, выбранный формат массива и размер буфера должны изучаться
совместно; причина пока не доказана. Результаты нужно воспроизводить, затем
решать, как привести output к плановой длине без потери реальных сэмплов.

DC на краях содержит заметные отклонения: первый frame 0.94289/0.98286,
последний 0.91764/0.92192 (soxr/samplerate); ошибка во внутренней области
после исключения 2048 frames по краям ≤ 3.58e−7 / 5.96e−8. Sweep дал 48000
frames и конечные значения для обоих; спектр не анализировался.

Для контекста обработан 1 kHz сигнал целиком и отдельно crop `[11025, 33075)`;
координата начала соответствует 12000 output frames ровно. Максимальная разница
на первых 256 frames 0.001986 / 0.001853, во внутренней области после отступа
2048 frames 3.28e−7 / 0 (soxr/samplerate). Эта разница иллюстрирует влияние
обработки границ, а не слышимый артефакт или доказательство конкретного padding.

## Что ещё не сделано

* Проверка предложенных zero extension, local-origin phase и неизменности при
  разных соседних сэмплах с полным reference oracle; выбранные API могут иметь
  иные граничные условия. Не утверждаем соответствие варианту A.
* Impulses на обоих краях, спектральные sweep-метрики, качественные passband/stopband метрики,
  контроль транзиентов, частоты и ratio, независимые эталонные векторы.
* Квалификация на Windows 10/11, Unicode/русские пути и прослушивание реальных
  разрешённых музыкальных записей. Не запускались внешние тесты библиотек.
* Сравнение time-stretch и pitch-shift; licensing decision и проверка DLL/source
  ещё открыты. Это исследование не означает, что какая-либо библиотека выбрана.
